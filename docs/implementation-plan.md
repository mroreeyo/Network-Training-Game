# 네트워크 학습 게임 구현 계획

기준 문서: `docs/네트워크 학습 게임 패키지 PRD.md` (2026-11-10)
작성일: 2026-11-10

## 1. 방향 요약

PRD가 정한 순서를 그대로 따르되, 각 단계가 끝날 때 확인할 수 있는 완료 기준을 붙였습니다. 핵심 전략은 다음 세 가지입니다.

1. **공통 틀과 챕터 1을 먼저 끝까지 완성합니다.** 챕터 1을 직접 플레이해 보고 "머리에 남는지" 판단한 다음에 챕터 2로 넘어갑니다. 이 시점이 계획 전체에서 가장 중요한 점검 지점입니다.
2. **게임 규칙(`rules/`)을 화면보다 먼저 만듭니다.** 정답 판정과 실패 이유가 순수 함수로 먼저 확정되면, 화면은 그 결과를 그리기만 하면 됩니다. 실패 이유 설명이 PRD에서 "핵심"으로 지정되어 있으므로, 판정 함수가 실패 문구의 재료까지 함께 반환하도록 설계합니다.
3. **규칙 위반을 사람의 눈이 아니라 도구로 잡습니다.** 30줄 함수, 중첩 삼항 연산자, 토큰 밖의 색·px 값, import 주석 누락은 린트와 검사 스크립트로 자동 확인합니다.

## 2. 개발 시작 전에 정할 사항

PRD의 열린 질문 2개와, 검토하면서 발견한 결정 사항을 함께 정리했습니다.

**확정 (2026-11-10)**: D1~D9를 모두 아래 표의 안대로 확정했습니다.

| # | 결정 사항 | 확정안 | 이유 |
| --- | --- | --- | --- |
| D1 | Pretendard를 CDN으로 불러올지, 프로젝트에 포함할지 (PRD 열린 질문) | jsDelivr의 Pretendard Variable **동적 서브셋** CSS를 버전 고정으로 불러옴 | 한글 글꼴 전체 파일은 수 MB라서 링크로 공유하는 정적 사이트에 부담이 큽니다. 동적 서브셋은 화면에 쓰인 글자 묶음만 받습니다. CDN이 실패해도 `sans-serif`로 대체되어 플레이에는 지장이 없습니다. |
| D2 | 챕터 4 조사 도구 결과를 실제 명령어 출력처럼 보여 줄지 (PRD 열린 질문) | **실제 출력 형식을 줄여서** 조사 기록지 위에 보여 줌. 글꼴은 Pretendard + `tabular-nums` 유지 | 디자인 원칙 1("용어는 실제 그대로")에 맞고, 실무에서 같은 출력을 다시 봤을 때 알아볼 수 있습니다. 검은 배경 터미널 모양은 금지 목록에 해당하므로 쓰지 않습니다. |
| D3 | 규칙 함수 테스트 도구 | **Vitest를 개발 의존성으로만 추가** | `rules/`를 순수 함수로 분리한 목적이 "따로 테스트하기"인데 PRD 기술 스택에 테스트 도구가 없습니다. Vite와 설정을 공유하므로 추가 설정이 거의 없고, 배포 결과물에는 포함되지 않습니다. 추가하면 기술 스택 표에 이유를 한 줄 적습니다 (규칙 3-4). |
| D4 | 별점 계산 방식 | 기본 1개 + 힌트 미사용 1개 + 실수 없음 1개. 힌트를 1단계든 2단계든 쓰면 "힌트 미사용" 1개만 잃음. 같은 스테이지는 **최고 기록**을 저장 | PRD의 "힌트 쓰면 별점 1개 감소"와 "별점 기준" 표를 동시에 만족하는 가장 단순한 해석입니다. |
| D5 | "실수"의 정의 | 챕터 1~3: 같은 스테이지에 들어와서 클리어하기 전까지 실패(반송)한 횟수. 챕터 4: 도구 사용 횟수가 스테이지의 최소 횟수를 넘은 경우 | 챕터마다 실수 개념이 달라서, 판정 결과에 `mistakeCount`를 담아 공통 별점 함수에 넘기는 방식으로 통일합니다. |
| D6 | 챕터 3의 룰 순서 바꾸기 방식 | 드래그 대신 **위로/아래로 버튼** | 목록 정렬 드래그를 하려면 `@dnd-kit/sortable`이라는 세 번째 라이브러리가 필요합니다. 버튼 방식은 키보드 접근성 요구도 그대로 충족합니다. |
| D7 | 라우터 방식 | `BrowserRouter` + 배포 설정에 모든 경로를 `index.html`로 돌리는 규칙 추가 (Vercel이면 `vercel.json`) | 이 설정이 없으면 스테이지 주소에서 새로고침할 때 404가 납니다. |
| D8 | React 자체의 import에도 사용 이유 주석을 달지 | 단다. 처음 도입한 `main.jsx`에 자세히, 나머지 파일에는 한 줄 요약 | 성공 기준이 "모든 라이브러리 import 위에 주석"이라서, 예외를 두면 검사 스크립트가 복잡해집니다. |
| D9 | 시안 제작 도구 | `tokens.css`를 그대로 쓰는 **정적 HTML 시안** | 시안 단계에서 토큰 값이 실제로 검증되고, 시안 CSS를 공통 컴포넌트 CSS로 옮겨 쓸 수 있습니다. |

## 3. 핵심 설계

### 3.1 화면 주소

| 주소 | 화면 | 비고 |
| --- | --- | --- |
| `/` | `WorldMapPage` | 허브 |
| `/chapters/:chapterId` | `StageListPage` | 잠긴 챕터면 월드맵으로 돌려보냄 |
| `/chapters/:chapterId/stages/:stageNumber` | `StagePage` | 잠긴 스테이지면 스테이지 목록으로 돌려보냄 |
| `/glossary` | `GlossaryPage` | 개념 도감 |

`chapterId`는 폴더 이름과 같은 `packet`, `subnet`, `firewall`, `detective`를 씁니다.

### 3.2 PRD 폴더 구조에 추가할 파일 2개

PRD 폴더 구조를 그대로 따르되, 챕터 공통 규칙과 챕터 목록을 둘 자리가 없어서 아래 2개 파일을 추가합니다.

- `src/rules/progressRules.js`: 챕터 해금 판정, 별점 계산, 클리어한 스테이지에서 개념 카드 목록 계산
- `src/data/chapters.js`: 챕터 순서, 이름, 물류 센터 장소 이름, 스테이지 데이터 연결

### 3.3 진행도 저장 형태

```js
// localStorage 키: 'network-game-progress'
// version을 두는 이유: 나중에 저장 형태가 바뀌어도 예전 기록을 옮길 수 있게 하기 위해서다.
const progress = {
  version: 1,
  clearedStages: {
    'packet-1': { stars: 3 },
    'packet-2': { stars: 2 },
  },
  seenTutorials: ['packet'],
};
```

- 개념 카드와 챕터 해금 여부는 저장하지 않고 `clearedStages`에서 계산합니다. 같은 사실을 두 곳에 저장하면 서로 어긋날 수 있기 때문입니다.
- `utils/storage.js`는 읽기 실패(사생활 보호 모드, 손상된 값)일 때 빈 진행도를 돌려주도록 만듭니다.

### 3.4 판정 결과의 공통 형태

모든 챕터의 판정 함수는 같은 모양의 결과를 돌려줍니다. 실패 이유가 PRD 문구 규칙(무슨 일 → 왜 → 다음 행동)의 세 부분으로 나뉘어 있어서, `ResultModal`이 챕터를 몰라도 실패 문구를 그릴 수 있습니다.

```js
const result = {
  passed: false,
  reason: {
    what: '패킷이 반송됐어요.',
    why: '라우터를 지났는데 이전 구간의 MAC 주소가 그대로예요.',
    next: 'L2 헤더를 새로 붙여 보세요.',
  },
  mistakeCount: 1,
};
```

### 3.5 StageLayout과 게임판의 약속

PRD에서 `StageLayout`이 "상단 바 + 게임판 + 힌트"(공통 컴포넌트 목록)와 "작업 지시서 / 작업대 / 부품 트레이"(화면 배치) 두 가지로 설명되어 있어서, 둘을 합쳐 아래처럼 정합니다.

```text
StageLayout
├─ 작업 지시서: StageHeader (스테이지 제목, 목표, 남은 횟수) + HintBox
├─ 작업대: 챕터별 게임판 (children)
└─ 부품 트레이: 챕터별 부품 (tray prop), 휴대폰에서는 화면 아래 고정
```

- 챕터별 게임판(`PacketBoard` 등)이 받는 props는 `stage`, `onFinish` 두 개로 통일합니다.
- 게임판은 판정이 끝나면 `onFinish(result)`만 호출합니다. 별점 계산, 진행도 저장, 결과 화면 띄우기는 `StagePage`와 `StageLayout`이 맡습니다.
- 이렇게 하면 챕터를 추가할 때 새로 만드는 것은 "게임판 + 규칙 + 데이터" 세 가지뿐입니다.

### 3.6 드래그와 "누르고 놓기"를 하나의 흐름으로

접근성 기준 3번(드래그 없이도 플레이)을 지키기 위해, 드래그와 클릭이 같은 함수를 부르게 만듭니다.

1. 게임판이 "지금 고른 카드" 하나를 `useState`로 가집니다.
2. `DraggableCard`를 누르거나 Enter/Space를 누르면 그 카드가 선택됩니다.
3. `DropZone`을 누르거나 그 위에서 Enter/Space를 누르면, 선택된 카드를 놓습니다.
4. 드래그로 놓아도 3번과 같은 `placeCard(cardId, zoneId)` 함수를 부릅니다.

### 3.7 모달은 브라우저 기본 `<dialog>`

`Modal`은 `<dialog>` 요소의 `showModal()`로 만듭니다. Esc로 닫기와 모달 바깥 조작 차단을 브라우저가 처리해 주므로, 포커스 가두기 코드를 직접 짜지 않아도 되고 라이브러리도 필요 없습니다.

## 4. 단계별 계획

각 단계는 "완료 기준"을 모두 만족해야 끝난 것으로 봅니다.

### 0단계. 준비와 시안

| 작업 | 산출물 | 상태 |
| --- | --- | --- |
| 2절의 결정 사항 D1~D9 확정 | 이 문서 2절 갱신 | 완료 |
| `tokens.css` 작성 (PRD 값 그대로) | `src/styles/tokens.css` | 완료 |
| 시안 3장: 월드맵, 챕터 1 스테이지, 결과 화면 (PC·휴대폰 각각) | `design/mockups/*.html` (결과 화면은 반송·통과 2개 파일) | 작성 완료, 확정 대기 |
| 시안을 화면 검수 체크리스트 6개 항목으로 점검 | `docs/design-review-phase0.md` | 완료 |

완료 기준: 시안 3장이 확정되고, 검수 체크리스트를 통과합니다.

남은 일: 시안을 직접 확인하고, 검수 기록 4절의 결정 사항 A~E를 정하면 0단계가 끝납니다.

### 1단계. 공통 틀

진행 순서가 중요해서 순서대로 적었습니다.

1. **프로젝트 세팅**: Vite React(JavaScript) 템플릿, React Router, `@dnd-kit/core`, (D3 결정 시) Vitest
2. **품질 장치** (6절): ESLint 규칙, 토큰 검사 스크립트, import 주석 검사 스크립트
3. **규칙과 저장**: `progressRules.js`(해금, 별점, 개념 카드 계산)와 `storage.js`, 각각의 테스트
4. **기본 컴포넌트**: `Button`, `Card`, `Modal`, `StarRating`, `ProgressBar`
5. **화면**: `WorldMapPage`(컨베이어 한 줄, 휴대폰에서는 세로), `StageListPage`
6. **스테이지 틀**: `StageLayout`, `StageHeader`, `HintBox`, `ResultModal`(도장 연출, `prefers-reduced-motion` 대응), `ConceptCard`
7. **드래그 부품**: `DraggableCard`, `DropZone` (3.6절 방식)
8. **시안 비교**: PC와 휴대폰(가로 360px) 화면을 캡처해 시안과 나란히 비교

완료 기준:

- 가짜 진행도를 넣었을 때 해금, 별점, 진행률이 맞게 표시됩니다.
- 새로고침해도 진행도가 유지됩니다.
- `lint`, `test`, 토큰 검사, import 주석 검사가 모두 통과합니다.

### 2단계. 챕터 1 패킷 택배 (점검 지점)

1. `packetRules.js`와 테스트를 먼저 작성합니다 (7.1절).
2. `packetStages.js`에 스테이지 5개와 힌트 2단계, 실패 문구를 작성합니다.
3. `PacketBoard`와 챕터 전용 부품(패킷 상자, 경로 표시)을 만듭니다.
4. 개념 카드 5장을 `conceptCards.js`에 작성합니다.
5. **직접 플레이 점검**: 다 깬 뒤 하루 정도 지나서 "라우터를 지나면 왜 MAC은 바뀌고 IP는 유지되는가"를 설명 없이 말할 수 있는지 확인합니다.

완료 기준: 스테이지 5개를 PC·휴대폰·키보드만으로 각각 끝까지 깰 수 있습니다. 5번 점검에서 개념이 남지 않았다면, 3단계로 넘어가기 전에 스테이지 구성이나 실패 문구를 고칩니다.

### 3단계. 챕터 2 서브넷 퍼즐

1. `subnetRules.js`와 테스트 (7.2절)
2. 스테이지 데이터 5개, 개념 카드 5장
3. `SubnetBoard`: /24 블록을 256칸 바닥 구역으로 그립니다.
4. **공통 컴포넌트 재사용 점검**: 챕터 폴더 안에 버튼, 카드, 모달 같은 UI가 생기지 않았는지 확인합니다.
5. 시안 비교를 반복합니다.

### 4단계. 챕터 3 방화벽 디펜스

1. `firewallRules.js`와 테스트 (7.3절)
2. 스테이지 데이터 5개, 개념 카드 5장
3. `FirewallBoard`: 룰 편집표(D6의 위로/아래로 버튼)와 웨이브 재생
4. 시안 비교를 반복합니다.

### 5단계. 챕터 4 장애 탐정

1. `detectiveRules.js`와 테스트 (7.4절)
2. 사건 데이터 5개, 개념 카드 5장. 4번 사건은 챕터 2의 `subnetRules.js` 함수를 재사용해 단서를 만듭니다.
3. `DetectiveBoard`: 사고 접수증, 조사 도구 버튼, 조사 기록지, 원인·계층 지목
4. 시안 비교를 반복합니다.

### 6단계. 마무리

1. `GlossaryPage`(개념 도감), `TutorialSteps`(챕터 첫 진입 시 3단계, 건너뛰기 가능)
2. 진행도 초기화 (PRD 문구 표의 확인 문구 그대로)
3. 접근성 기준 6개 전체 점검: 대비, 44px 영역, 드래그 없는 플레이, 포커스 표시, 모달, 200% 확대
4. 휴대폰 360px에서 4개 챕터 전체 플레이
5. 배포 (D7의 경로 설정 포함)와 성공 기준 5개 점검

## 5. 작업량을 줄이는 순서 원칙

- 챕터마다 **규칙 → 데이터 → 게임판** 순서로 만듭니다. 규칙 테스트가 통과한 뒤에 화면을 만들면, 화면 버그와 규칙 버그가 섞이지 않습니다.
- 스테이지 1개를 끝까지 완성한 다음에 나머지 4개를 데이터로 추가합니다. PRD 개발 규칙 1-7("스테이지 추가 = 데이터 추가")이 실제로 지켜지는지 이 시점에 드러납니다.

## 6. 품질 장치 (리뷰 전에 자동으로 잡기)

새 런타임 라이브러리 없이, Vite 템플릿에 포함된 ESLint와 Node 스크립트만 씁니다.

| 개발 규칙 | 자동 확인 방법 |
| --- | --- |
| 함수 30줄 이하 | ESLint `max-lines-per-function` (빈 줄·주석 제외 30) |
| 삼항 연산자 중첩 금지 | ESLint `no-nested-ternary` |

`package.json`에 `check` 스크립트 하나로 묶어서, 커밋 전에 한 번에 돌립니다.

## 7. 챕터별 설계 메모

### 7.1 챕터 1. 패킷 택배

- **게임 흐름**: 출발 PC에서 헤더 카드를 L4 → L3 → L2 순서로 붙입니다. "패킷 보내기"를 누르면 상자가 다음 장비로 이동하고, 라우터에서는 L2 라벨을 떼고 다음 구간의 L2 라벨을 새로 붙여야 다시 보낼 수 있습니다.
- **학습 장치**: 부품 트레이에 MAC 주소가 다른 L2 카드 여러 장과, 목적지 IP를 라우터 IP로 잘못 적은 L3 카드를 함께 둡니다. 흔한 오해를 직접 고르게 만들어야 실패 문구가 학습으로 이어집니다.
- **규칙 함수 후보**: `checkHeaderOrder`, `getSegmentMacAddresses`, `checkLinkHeaderForSegment`, `checkTransportChoice`, `checkDecapsulationOrder`
- **데이터 형태**: 경로(장비 목록), 구간별 출발·목적지 MAC, 부품 트레이 카드 목록, 힌트 2단계, 실패 문구

### 7.2 챕터 2. 서브넷 퍼즐

- **게임 흐름**: 부서를 고르고, 프리픽스(/25~/30)와 시작 주소를 정해 바닥 구역에 구역선을 긋습니다. "구역 확정하기"를 누르면 판정합니다.
- **주의할 함정**: 자바스크립트의 비트 연산(`&`, `>>`)은 32비트 부호 있는 정수로 계산해서 `192.x.x.x` 같은 주소에서 음수가 나옵니다. 곱셈·나눗셈과 `Math.floor`로 계산하면 이 문제를 피하고, "쉬운 코드" 규칙에도 맞습니다.
- **추가 제안**: PRD의 실패 조건(호스트 부족, 겹침, 블록 밖)에 **경계 불일치**(예: 192.168.0.70은 /26의 시작 주소가 될 수 없음)를 더하면 좋겠습니다. 서브넷 시작 주소가 블록 크기의 배수여야 하는 이유가 VLSM의 핵심이기 때문입니다.
- **규칙 함수 후보**: `convertIpToNumber`, `convertNumberToIp`, `getNetworkAddress`, `getBroadcastAddress`, `calculateHostCount`, `isSameNetwork`, `isAlignedToPrefix`, `findOverlappingRanges`, `isInsideBlock`

### 7.3 챕터 3. 방화벽 디펜스

- **게임 흐름**: 웨이브 전에 룰 표를 작성하고 순서를 정합니다. "룰 적용하기"를 누르면 판정은 한 번에 계산하고, 화면은 그 결과를 상자가 컨베이어를 지나가는 모습으로 순서대로 보여 줍니다. 동작 줄이기 설정이면 결과만 바로 보여 줍니다.
- **판정을 먼저, 연출은 나중에** 하는 이유: 판정이 애니메이션 타이밍에 묶이면 테스트할 수 없고 버그도 찾기 어렵습니다.
- **규칙 함수 후보**: `doesRuleMatchTraffic`, `findFirstMatchingRule`, `decideTrafficAction`(일치하는 룰이 없으면 기본 차단), `runWave`, `judgeWaveResult`
- **데이터 형태**: 웨이브별 트래픽 목록(출발지, 목적지, 포트, 프로토콜, 방향, 공격 여부), 정상 트래픽 차단 허용 개수, 처음부터 주어지는 룰(3번 스테이지처럼 순서가 틀린 룰 목록)

### 7.4 챕터 4. 장애 탐정

- **게임 흐름**: 사고 접수증을 읽고 도구(ping, nslookup, 포트 확인, 경로 추적, 케이블·링크 확인)를 대상에 사용해 단서를 모은 뒤, 원인과 계층을 지목합니다.
- **결과 화면 제안**: 플레이어가 도구를 쓴 순서와 "아래 계층부터 확인하는 권장 순서"를 나란히 보여 줍니다. PRD 학습 목표에 진단 순서가 있지만 실패 조건에는 반영되어 있지 않아서, 결과 화면에서라도 비교하게 하면 학습 목표가 빠지지 않습니다.
- **규칙 함수 후보**: `runInvestigationTool`, `isOverToolLimit`, `judgeDiagnosis`(5번 사건은 원인 2개 모두 맞혀야 통과)
- **데이터 형태**: 사건 설명, 숨겨진 원인과 계층, 도구·대상별 출력(D2의 줄인 실제 출력), 최소 도구 횟수와 최대 도구 횟수

## 9. PRD 검토 결과

### 9.1 색 대비 재계산

WCAG 2.1 공식으로 PRD 접근성 표의 10개 조합을 다시 계산했고, 모두 PRD에 적힌 값과 일치했습니다. 다만 표에 없는 조합 중에서 아래 3개는 구현할 때 주의해야 합니다.

| 조합 | 대비 | 기준 | 구현 시 조치 |
| --- | --- | --- | --- |
| 테이프색 L3 계층 띠 / 흰 운송장 | 1.62:1 | 도형 3:1 | 띠에 잉크 테두리를 두르거나, 띠와 운송장 사이에 잉크 선을 긋습니다. 띠 위 "L3" 글자는 잉크색(9.21:1)으로 씁니다. |
| 테이프색 DropZone 강조 / 바닥 | 1.33:1 | 도형 3:1 | 강조 상태에서도 점선 잉크 테두리를 반드시 유지합니다. |
| 잉크 글자 / 컨베이어색 | 2.51:1 | 글자 4.5:1 | 주 버튼 글자는 흰색만 씁니다 (5.93:1). |

참고로 포커스 외곽선(컨베이어색)은 바닥 위에서 4.87:1, 흰 면 위에서 5.93:1이라 기준 3:1을 넘습니다.

### 9.2 PRD 보완이 필요한 부분

1. 별점 기준과 힌트 감점 규칙의 관계가 모호합니다 (D4로 해석을 정함).
2. 챕터마다 "실수"의 의미가 다릅니다 (D5로 정함).
3. 테스트 도구가 기술 스택에 없습니다 (D3).
4. 폴더 구조에 공통 규칙과 챕터 목록을 둘 자리가 없습니다 (3.2절).
5. `StageLayout` 설명이 두 곳에서 다릅니다 (3.5절에서 합침).
6. 챕터 3의 룰 순서 드래그는 세 번째 라이브러리를 요구합니다 (D6).
7. 정적 호스팅에서 `BrowserRouter`를 쓰려면 경로 설정이 필요합니다 (D7).
